How the Strip Width Tools Work

NB the 'strip_geom.py' tool is working well, but strip_solver.py needs work. 

These two small desktop tools calculate the ground strip visible in an oblique calibration photo. The camera and lens are known; the tilt angle and height above ground are not (or one is known but not the other). Both tools are designed to recover the missing pose (camera angle and height) from the same clue — how equally spaced ground markers get squeezed together by perspective.

The problem

In a calibration pass, we are mainly interested in strip width: how many metres of ground the photo covers, from its bottom edge (nearest the aircraft) to its top edge (farthest). Animal densities are computed per strip area, so an error in strip width becomes an error in the population estimate.

Strip width depends on three things: focal length, height above ground (AGL), and the camera’s oblique angle off-nadir (i.e away from a straight-down angle). Only the first is truly known, but there are some other parameters under our control which we can use:

Known and trusted

  • Focal length and sensor size — together these give the focal length in pixels, f
  • Marker spacing on the ground, d (because we laid them out and carefully measured their distances)

Not known precisely

  • Tilt angle φ — perhaps mounted at 45°, but the aircraft rolls; could be 42–48°.
  • Height AGL h — the altimeter target, but terrain and flying vary it by up to ±10%

A 3° tilt error or a 10% height error each shift the strip width by tens of metres. So neither tool takes tilt or AGL on faith — they measure them, from the photo itself.

Perspective compression is a measurement

Markers are laid on the ground in a line perpendicular to the flight path, at known equal spacing. In the photo, those equal spacings come out unequal: the farther a marker is, the more its gap to the next marker is compressed into fewer pixels. The exact pattern of that compression depends on h and φ – which means the pattern can be read backwards to find them.

Both tools use the flat-ground pinhole relation between a marker’s ground distance from nadir Y and its pixel coordinate t (measured from the image centre along the marker line, positive toward the far edge), with u = tan φ:

t = f·(Y − h·u) / (h + Y·u)

In both tools you click the markers, and each tool extrapolates its fitted model to the photo’s bottom and top edges and converts those two pixel positions back to ground distances. Strip width is their difference. Where the tools differ is in how many unknowns the markers can pin down.

strip_geom.pyCalibration: enough markers to solve everything

On a calibration flight the whole marker line is visible - you need a minimum of 4, and ideally more markers. Written in terms of the distance y along the marker line (marker i is at y = i·d), the pinhole relation becomes a three-parameter curve:

t = (a·y + b) / (c·y + 1)

The tool least-squares fits a, b, c to your clicks. Those three numbers are not just curve-fitting constants — the camera pose can be read straight out of them:

h = f·(a − b·c) / (a² + c²·f²) tan φ = c·f / a

Both formulas are indifferent to where the first marker happens to sit relative to nadir — that unknown offset drops out. So the calibration tool needs no assumptions at all: height, tilt and strip width all come from the clicks plus the trusted focal length. The nominal tilt you enter is used only for an independent analytical cross-check, never in the fit.

In the worked example (markers synthesised at exactly 1000 ft and 45°), the fit returns a = 14.87, b = −729.1, c = 0.00178 — which decode to h = 304.8 m (1000 ft), φ = 45.00°, strip width 310.5 m, matching the analytical value exactly.

strip_solver.pyCalibration passes with only two markers and one setup assumption

Sometimes you can only see two markers, for example the runway side markers often set out at 50m or 60m (this varies, check carefully - you can even use Google Earth for a good estimation!).

On a single calibration pass perhaps only two markers are visible — not enough to solve height, tilt and the line’s offset from nadir. The solver’s move is to trade one assumption for the rest: fix the tilt at its nominal value from the mount (and flight data), and let the markers solve the height. Two markers at pixel positions t₁, t₂ separated by ground distance d give AGL in closed form:

h(φ) = d·(f − t₁u)·(f − t₂u) / ( f·(t₂ − t₁)·(1 + u²) )

The markers’ unknown offset from nadir cancels out of this formula exactly — it does not matter where in the frame the pair sits. With 3+ markers the same model is refined by least squares, which also yields a real RMSE.

Notice the role reversal: the AGL you assumed from flight data is no longer an input to the geometry. It is demoted to a sanity check — the tool warns if the solved AGL differs from it by more than ±10%, which usually means a wrong marker spacing, wrong click order, or a badly wrong tilt.

**Note that it is entirely possible that we might know AGL (from a laser altimeter) but not the φ angle - a new version of this tool will allow that caculation going the other way.**

Handling the tilt uncertainty

The one assumption left is the tilt, and it is honest about being uncertain: you give a plausible range (say 42–48°). The solver sweeps that range, and at every angle it re-solves the height from the markers before computing strip width. That coupling is what makes the result tight:

Both tools share the same assumptions worth remembering: flat ground across the strip, a trusted focal length, and markers clicked accurately along their line. The calibration tool also quietly assumes the marker line is straight and truly at the entered spacing — errors there masquerade as height errors. Per the README, results are looking good with 50 mm lenses but are still being tested.
